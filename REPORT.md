## 1. Анализ текущих проблем


1.  В названиях папок нет метрик. Непонятно, какая модель лучше, пока не заглянешь внутрь если там вообще есть логи.
2.  Версии названы рандомно: кто-то v1, кто-то v_123, кто-то вообще по названию датасета. Найти нужную версию программно почти невозможно.
3.  Неизвестно, что из этого уже крутится в продакшене, что было просто экспериментом, а что вообще сломано.
4.  Всё лежит на одной машинке. Если диск сломается или кто-то случайно нажмет rm -rf, компания потеряет наработки всех команд. К тому же, место на диске не резиновое.
5.  Нет связи с кодом. Неясно, на каком коммите или на каких параметрах обучалась конкретная папка.

## 2. Требования к системе

Исходя из этих проблем, я составил список требований для будущего Registry.

### Функциональные:
*   Регистрировать модели: Создавать карточку модели и добавлять туда новые версии.
*   Хранить всё отдельно: Метаданные (параметры, метрики) - в базу, тяжелые файлы (веса) - в отдельное хранилище.
*   Управлять стадиями: У каждой версии должен быть статус (Development, Staging, Production, Archived). Причем Production должен быть только один.
*   Давать скачивать файлы: Чтобы сервис деплоя мог легко забрать нужные веса по API.

### Нефункциональные (какой система должна быть):
*   Надежной: Использовать S3-хранилище вместо локальных папок.
*   Удобной: Наличие простого Python SDK, чтобы дата-саентисты не мучились с HTTP-запросами вручную.
*   Быстрой: Поиск по метрикам в базе должен быть мгновенным.

### Обоснование
*   FastAPI: Самый быстрый способ написать API на Python. Из плюсов - автоматическая документация, через которую удобно тестировать эндпоинты.
*   PostgreSQL: Нам нужны связи (модель -> версии). Плюс там есть тип JSONB, в который удобно кидать метрики и параметры обучения, так как у разных команд они могут отличаться.
*   MinIO: Это self-hosted аналог S3. Я выбрал его, потому что хранить гигабайты весов в обычной базе - плохая идея, а просто в папках - ненадежно.
*   Docker Compose: Чтобы всё это поднималось одной командой и работало в изолированных контейнерах.

## 4. База данных и API

### Схема БД
Я спроектировал две основные таблицы:
1.  Registered Models: Здесь храним общую информацию (название, какая команда создала, описание).
2.  Model Versions: Здесь самое интересное. Версия, ссылка на файл в MinIO, JSON-поле с метриками и текущий статус (Stage).

### API эндпоинты
Я решил сделать минимально необходимый набор:
*   POST /models - создать новую модель в реестре.
*   POST /models/{name}/versions - добавить новую версию. Тут важный момент: API не принимает сам файл, а отдает временную ссылку (Presigned URL), по которой SDK само загружает веса в MinIO. Это разгружает сервер.
*   PATCH /models/{name}/versions/{v}/stage - сменить статус (например, выкатить в прод).
*   GET /models/{name}/production - короткий путь для сервисов, чтобы сразу получить актуальную модель.
